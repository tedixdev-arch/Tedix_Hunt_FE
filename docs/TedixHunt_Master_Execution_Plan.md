# TedixHunt Master Execution Plan

Operational task manager for architecture v3.6. This register is the only current execution/status authority. Detailed requirements, frozen reconciliation records and historical mappings are in the [reconciliation report](TedixHunt_Execution_Plan_Reconciliation.md); the superseded [Master Control Plan](TedixHunt_Master_Implementation_Control_Plan_v3.md) and [Dependency Matrix](TedixHunt_Execution_Dependency_Matrix.md) remain historical evidence. Architecture requirements remain binding; report conflicts rather than guessing a resolution.

## A. Execution rules

1. Every implementation references an existing authorized Task ID in §C. No Task ID means no implementation. New tasks or container children require Product Owner approval before registration.
2. Verify dependencies and open/ongoing work before starting. Preserve documented order; change eligibility only because of a recorded dependency, never to maintain momentum.
3. Stay within the bounded deliverable. Necessary supporting tests/types/refactoring are allowed only when they add no separate feature. Reuse working behavior and keep interfaces simple and ergonomic.
4. Report blockers and conflicts; do not bypass contracts, approval/safety rules or activation gates with assumptions, hidden routes or flags.
5. Codex delivers a bounded Draft PR for ChatGPT review; the Product Owner controls merging. Deployment requires separate authorization and verification.
6. Record contract/decision, backend, frontend, integrated workflow and deployed E2E independently. A merged backend/contract/FE slice does not close another layer or its parent. Preserve completed source history after a deployment failure.
7. Only the Product Owner may change major scope, architecture, execution priority or governance. Preserve legacy/Signal content, exact approvals and immutable copies/snapshots.
8. After a verified change update only the affected record/dimension and evidence; derive the dashboard from §C. Follow the [closing loop](TedixHunt_Master_Implementation_Control_Plan_v3.md#7-update-the-master-architecture-plan--mandatory-closing-loop) for architecture/API/audit synchronization. No untracked manual DB changes.

## C. Authoritative task register

Records remain in the reconciled order: 109 original rows, 35 F7/G4/D10 slices, 23 H–N entries, then existing C6b-2 and the Product Owner approved F7-BE-01 prerequisite. There are 169 records: 57 parent workstreams and 112 executable/control records. A parent is an aggregate, not a duplicate code task. H–N and governance containers authorize only their recorded bounded contract/verification/decision action; no undefined `.1` child or whole-feature implementation is authorized.

**Reading the records:** dependency, acceptance and blocker links are binding parts of each record. `Details` opens that task's complete preserved fields (including exact APIs, tests, legacy/security checks and PR boundary). `Requirements` links its acceptance; read both before prompting implementation. Original action/priority, parent-child mappings and detailed foundation qualifications are retained there. Where no predecessor IDs were documented, use the named architecture section and §20 gates; do not invent predecessors.

**Evidence dimensions:** the status column describes only the recorded layer/action. For partial foundations, verification remains not started. Source-complete rows retain their bounded implementation history. Integration and deployed E2E remain unverified unless a separately dated evidence record says otherwise; historical onboarding claims do not become fresh verification. Contract/BE prerequisites keep their own completion boundary. Exact unchanged dimension qualifiers are preserved in each task's detail record.
